# 部署、安全与卸载

## 部署流程

1. 备份 Komari 数据目录和通知配置，确认服务端为 1.6.1。
2. 在插件管理上传构建产物 ZIP，核对 SHA-256 和权限。
3. 启用插件，打开“插件功能 / GFW 配置”。默认不执行探测。
4. 配置 3 个大陆、2 个非大陆 TCP 目标并选择服务器。
5. 确认系统通知已启用、已配置可用渠道，通知模板包含 `{{message}}`。
6. 先发送测试消息，再开启监测，从总览确认 5 个目标开始上报。

## 选择目标

使用已获准连接、长期开放 TCP 端口的目标。大陆目标宜来自不同运营商和网络；非大陆目标也应相互独立。域名由每台 Agent 本地解析，因此不同服务器可能实际连接不同 IP。DNS 故障也会表现为 TCP 探测失败，域名模式不是 IP 封锁的确证。

不要填写 HTTP URL、路径或用户名密码。合法示例：`probe.example.com:443`、`203.0.113.10:443`、`[2001:db8::1]:443`；这些是文档保留地址，并非可用的默认探测目标。

## 严格模式

在配置中启用严格模式并选择一个或多个境内 Komari 服务器。为每台受检服务器设置实际开放的测试端口；地址默认使用其 Komari IPv4，只有无 IPv4 时才使用 IPv6，也可填写自定义地址。源/目标地址族和网络路径须自行确认。

插件不会开端口或改防火墙。先确认选定境内探针能正常连接测试端口，再启用监测。正向大陆全失败、全部反向失败且非大陆仍可达，才进入被墙连续确认；解除要求全部正向和反向成功。探针离线时等待数据，不自动改变告警状态。

## 隐私

脱敏开关控制插件通知和总览中的服务器地址。IPv4 隐藏后两段；IPv6 隐藏后半部分。Komari 自身原有页面及其它插件的输出不受本插件控制。

系统通知使用空 Client 列表，仅携带已脱敏消息。管理员接口虽然可能返回完整服务器对象，插件只保留 UUID、名称、地址和分组所需数据，不持久化 token，不输出原始 RPC 响应到日志。

## 暂停与卸载

优先在配置页关闭监测并等待任务暂停成功，再禁用或卸载插件。需要删除探测历史时，使用“清理插件任务”；该操作仅删除拥有标识匹配的任务，且应明确确认。

宿主崩溃或强制删除插件可能使 unload 无法完成。此时到延迟监测页按 `[Komari GFW:` 前缀核对插件专属任务，停止其服务器绑定；不要删除不属于本插件的任务。

插件卸载会删除宿主的插件长期数据目录，告警历史也会丢失；需要保留时先备份 `data/plugin-data/komari-gfw`。正常更新 ZIP 保留该目录。

## 运行限制

如果 Agent 与 Komari 的连接本身中断，插件只能看到数据不足，不能可靠判定被墙。应保证 Komari 控制通道可用，并保留原有离线告警作为补充。

系统通知接口在总开关关闭或渠道为 none 时可能返回成功但不投递，因此插件应先检查配置。通知被渠道接受不等于终端用户已阅读；网络超时后的重试也可能造成重复投递。
