# 被墙检测

Komari 的服务器被墙检测插件。基于已有 Agent 的 TCP 探测，结合大陆与非大陆目标判断连通性异常，通过系统通知渠道发送疑似被墙及恢复通知，并提供管理总览。

最低支持 **Komari 1.6.1**，manifest 约束为 `>=1.6.1`，不因宿主版本更高而拒绝加载。实际宿主验证版本为 **1.6.1**，后续版本仍需兼容性验证。无需修改 Komari 核心或 Agent，也无需在受检服务器上额外安装脚本。

> “疑似被墙”是 TCP 连通性推断，不是封锁原因的确证。路由、DNS、目标服务及防火墙故障也可能影响结果。

## 核心功能

- **多目标检测**：自定义 3 个大陆目标和 2 个非大陆目标，支持域名、IPv4、IPv6 与端口。
- **按需监测**：受检服务器和境内探针均支持搜索、紧凑行和限高内部滚动，适配桌面与手机；新服务器不会自动加入。
- **逐台正向检测**：全局正向开关下选择境内探针，再独立开启需要正向检测的服务器。双向检测区分反向墙、正向墙和双向墙；单向异常及方向变化也会连续确认后通知。
- **告警与恢复通知**：复用 Komari 系统通知渠道，连续多轮确认后通知，避免短时抖动和重复告警。
- **IP 脱敏**：通知和总览可隐藏 IPv4 后两段，IPv6 隐藏后半部分。
- **管理总览**：在“插件功能 / 被墙检测总览”查看服务器状态、各方向结果和最近事件；配置位于统一的“插件配置”页面。

## 检测规则

- **反向**：受检服务器主动连接 3 个大陆目标。
- **非大陆对照**：受检服务器主动连接 2 个非大陆目标。
- **正向**：全局正向开关和该受检服务器的独立开关均开启时，选定的境内探针主动连接其测试端口。

未实际开启正向检测的服务器仅使用 5 个主动目标：大陆 0/3、非大陆至少 1/2 成功时连续确认告警，状态为“疑似被墙”；可改为非大陆必须 2/2 成功。解除要求 5 个目标全部成功，不等待正向样本。

实际开启正向检测的服务器同样要求非大陆对照达到成功条件，并按以下组合区分状态：

| 反向大陆目标 | 正向境内探针 | 状态 |
| --- | --- | --- |
| 0/3 成功 | 全部成功 | 疑似反向墙 |
| 3/3 成功 | 全部失败 | 疑似正向墙 |
| 0/3 成功 | 全部失败 | 疑似双向墙 |

单向异常、双向异常和方向变化均使用“告警连续次数”确认，不同方向不混用计数。方向变化不会先解除旧告警，异常持续时间从最初告警累计。解除要求反向 3/3、非大陆对照 2/2 和全部正向探针连续成功；同方向部分成功、缺失或过期结果不判墙，也不解除旧告警。

默认每 60 秒探测，告警和恢复均连续确认 3 轮。缺失、离线、过期或错位样本不算失败，也不能解除告警；首次正常不发恢复通知，全部失败不判为被墙。新服务器不会自动加入。

通知标题为“服务器疑似被墙”“服务器被墙方向变化”和“服务器解除被墙状态”，包含服务器名、IP、状态和各方向结果；方向变化会列出前后状态。通知正文不附加说明段落。默认隐藏 IPv4 后两段，如 `203.0.*.*`；IPv6 隐藏后半部分。脱敏作用于通知和插件总览。

## 安装配置

1. 备份 Komari 数据，确认服务端为 **1.6.1 或兼容的更高版本**。
2. 从 [Releases](https://github.com/Connor3773/Komari_GFW/releases/latest) 下载对应版本的 `komari-gfw-版本号.zip` 和 `SHA256SUMS`，或使用本地构建包。核对 SHA-256 后在插件管理上传 ZIP，并批准声明的权限。不要使用 GitHub 自动生成的 Source code 压缩包。
3. 启用插件，打开“插件配置”，选择“被墙检测”。首次安装监测关闭。
4. 修改目标、选择受检服务器。需要双向检测时开启“正向检测全局开关”，在其下选择境内探针，再为需要的服务器勾选“正向检测”并设置实际开放的测试端口；其余服务器继续仅反向检测。
5. 在系统中配置通知渠道，模板包含 `{{message}}`，先发送测试通知。
6. 开启监测，使用表单内的“保存配置”，在“插件功能 / 被墙检测总览”查看结果。

配置和总览仅管理员可见，配置入口为 `/admin/plugins/config?short=komari-gfw`。两种服务器列表都可按名称、分组或显示 IP 搜索；筛选不改变已选项目。全局正向关闭时，逐台正向开关、测试端口和地址全部隐藏；重新开启后恢复原有选择。只有全局和逐台正向开关都开启时才显示端口与地址，端口必填、地址可选；关闭任一开关不校验隐藏字段的必填/有效地址，也不丢弃已填写值，保存、刷新后重新开启仍恢复。

从 0.1.0 至 0.1.5 升级时直接覆盖上传，不要先卸载或清空插件存储。内部 ID `komari-gfw`、任务标识和 schema 1 保留，已有配置无需重填。0.1.3 新增 `allowHooks`，从更早版本升级后必须重新批准权限并启用插件；0.1.4 至 0.1.6 没有新增权限。审批前和插件禁用时过滤不生效。升级后刷新已打开的服务器详情、后台延迟监测及配置页面，已有浏览器/CDN 缓存不会被插件追溯删除。

**0.1.6 配置迁移：** 原严格模式开关保留为正向全局开关。旧版严格模式已开启时，原受检服务器的独立正向开关自动开启，端口、地址和告警保留；旧普通模式保持仅反向检测。新增选择的服务器默认不启用正向检测。新版本允许混合配置，若需降级到不认识逐台开关的旧版，请恢复升级前备份，不要原样套用新配置。

**0.1.5 严格模式规则变化：** 不再只对双向失败告警，单向墙及方向切换也会通知。原有严格模式未解除告警按“双向墙”兼容，不因升级重发；新的方向须重新达到连续次数阈值。旧版尚未确认的失败计数从新鲜轮次重新开始，已有告警和异常起点保留。关闭严格模式（含删除探针后的自动关闭）改为普通被墙表述，不因此产生解除通知。

1.6.1 覆盖安装启用中的旧版时，可能提示 `plugin reinstalled but reload failed: ... permissions require approval`：这表示新包已安装但权限变化阻止了自动重载，不是配置丢失。确认版本已更新后重新审批并启用，检查总览即可。

成功读取完整服务器列表后自动移除已删除服务器的选择、独立开关、端口、地址和检测状态，不把离线或列表接口错误当作删除。已选境内探针被删除时自动关闭正向全局开关，剩余受检服务器继续仅反向检测；逐台开关和输入保留，不自动重新开启全局开关。最后一台受检服务器删除后关闭监测，并删除无用途的全部插件任务与历史，不留下空绑定任务。现存服务器的未解除告警保留，受影响的计数和待发通知重新确认；删除本身不发送恢复通知。调整提示显示一次，约 8 秒消失并自动确认已读，无需保存配置；真正的错误不会自动隐藏。旧页面若提示版本冲突，刷新后重试。

### 默认目标

```text
大陆电信  gd-ct-v4.ip.zstaticcdn.com:80
大陆联通  gd-cu-v4.ip.zstaticcdn.com:80
大陆移动  gd-cm-v4.ip.zstaticcdn.com:80
非大陆    1.1.1.1:443
非大陆    9.9.9.9:443
```

支持 `域名:端口`、`IPv4:端口`、`[IPv6]:端口`，不接受 URL、路径或凭据。域名由 Agent 本地解析；默认大陆目标同处广东，不能代表所有地区。仅使用获准连接的目标，按需增加地域独立性。

正向测试地址只填域名或 IP，不带协议、路径或端口。手动地址优先；留空时使用 Komari 登记的 IPv4，无 IPv4 时使用 IPv6，登记 IP 变化自动同步对应任务并重新确认该服务器。插件不会开放端口或修改防火墙；境内探针需要独立、稳定的控制连接，不能探测自己。登记 IP 不一定等于实际出站 IP，混合地址族结果不能证明某个 IP 已解封。

## 权限与数据

系统 RPC 用于管理专属 TCP 任务、读取检测结果、发送通知和定向清理历史；路由权限用于提供管理员配置和总览接口；`allowHooks` 用于过滤指定 Ping HTTP/WS 输出；Node 兼容模块用于本地状态存储及摘要计算。插件不执行远程命令，不修改服务器防火墙。

- 不建立延迟历史副本：每个目标只持久化最新值、去重游标及必要告警状态。
- 保留本实例已确认任务的 ID 集合和必要删除凭据，用于屏蔽缓存/遗留记录；不保存另一份探测历史。确认 ID 被用户任务复用或改名后撤销过滤与清理归属。
- 已处理事件仅保留 7 天、最多 100 条；有效待发通知额外保留最多 24 小时。历史到期不会解除仍在持续的告警。
- 每小时通过宿主官方数据库 RPC，精确清理本插件任务超过 1 小时的**已结束聚合桶**。保留近期和仍在聚合的数据，不修改全局保留策略，不清理其它任务。批量删除有上限，大量旧数据可能分多轮清理。
- 原生任务删除后会留下指标序列字典。对有明确归属和删除凭据的任务，至少保护 48 小时后，每小时最多检查 20 个：核验无活跃同 ID 任务、无最近 10 分钟原始样本，再回收超过保护窗口的遗留 Ping 聚合行及空的对应序列字典。无残留才释放隐藏 ID；近期数据、错误或未知结构继续保留保护。旧版只有隐藏 ID、没有删除凭据的项目不会猜测回收。
- 不删除指标定义、共享标签/粒度字典或用户序列，不执行全库 VACUUM。清理释放的页可复用，文件不一定立即缩小。清理失败显示提示并重试，检测与告警继续运行。
- 移除受检服务器或关闭其有效正向检测时，删除无用专属任务与历史，清除失效映射。仅暂停监测时保留仍需恢复的任务；删除失败的旧任务先暂停，记录重试状态，重载后继续重试。

卸载前先保存关闭监测，按需使用“清理插件任务”，再禁用或卸载。宿主异常退出或强制删除插件可能跳过清理；人工处理时按 `[Komari GFW:` 所有权前缀核对，勿删其它任务。

## 内部任务隐藏与边界

0.1.3 在普通 Ping HTTP 接口及 `/api/rpc2` 的 HTTP、WebSocket 输出中移除当前实例的内部任务、记录、指标系列及统计。0.1.5 补齐后台 `/api/admin/ping`（含尾斜杠）及 `admin:getAllPingTasks`：原生延迟监测的任务视图、服务器视图、绑定任务选择器及托管配置中的 Ping 任务选项均不再列出插件任务。后台仪表盘沿用已过滤的公共 Ping 接口。普通任务及其编辑、排序、绑定不变。

插件配置页和总览继续显示检测结果，内部 `server.call()` 读取原始数据，不修改核心、主题或 Agent，不通过删除有效数据隐藏任务。数据库/备份等特权数据仍含原生任务，不能承诺管理员直接查库也不可见。

识别依据为完整的 `[Komari GFW:<实例>:<槽位>]` 标识与已持久化任务 ID，不仅按名称包含 `GFW` 删除。暂停检测仍保持隐藏，但必须让插件本身处于启用状态。丢失实例存储的旧任务、其它实例的任务不能可靠认领，不自动隐藏或删除，需管理员核对处理。

**这不是严格的数据访问隔离，无法承诺所有请求下绝不暴露。** 1.6.1 根据 `Connection: Upgrade` 与 `Upgrade` 请求头跳过 HTTP hooks，普通 REST 端点带这两个头也可返回未过滤数据，不需要真正建立 WebSocket。HTTP 超过 32 MiB、流式及钩子超时/异常可能原样透传；WebSocket 超过 8 MiB 或单帧处理超过 1 秒也可能透传。其它插件转发原始数据、插件被禁用/卸载、未来新增入口同样不在保证内。上限由宿主控制，manifest 的 `maxHTTPBodyBytes` 不能解除它们。

已识别的不兼容结构/分页返回明确过滤错误，并在配置/总览显示告警，不伪造统计或默默忽略；宿主直接跳过钩子的情况无法由插件可靠检测。详细覆盖清单、性能代价和不修改核心/Agent 的替代路线见 [架构说明](docs/ARCHITECTURE.md#输出过滤与边界)。

npm ci
npm run check
